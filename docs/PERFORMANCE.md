# 性能計測

## モザイクの行スライス化 (2026-09-27)

`raster::apply_mosaic` の画素ごとの座標・境界判定を行単位にまとめた。
選択マスクも同じ行のスライスと突き合わせ、選択なし・アルファロックなしの
行は一括で埋める。選択 bbox に掛からないブロックは処理しない。
本処理に新たなバッファ確保や依存 crate は追加していない。

測定環境: Linux x86_64、Intel Core i9-12900KS、Rust 1.98.1、リリース設定。
変更前は `37c3a91` の処理に同じ計測用テストを追加して測った。
4000×4000 の固定シードの RGBA 画像を使用し、各条件でウォームアップ 1 回の後、
5 回の中央値を記録した。入力画像の復元・バッファ確保は計測時間に含めない。
マスク付きの条件では画像全体を bbox とし、7 画素に 1 画素を未選択とする。

| 条件 | ブロック幅 | 変更前 | 変更後 |
|---|---:|---:|---:|
| 全面 | 4 | 50.79 ms | 48.02 ms |
| 全面 | 40 (この画像サイズの自動値) | 35.34 ms | 22.51 ms |
| 全面 | 100 | 35.30 ms | 22.65 ms |
| 選択マスク | 4 | 69.75 ms | 56.14 ms |
| 選択マスク | 40 | 50.31 ms | 28.79 ms |
| 選択マスク | 100 | 49.39 ms | 27.91 ms |
| 選択マスク + アルファロック | 4 | 71.24 ms | 58.65 ms |
| 選択マスク + アルファロック | 40 | 53.02 ms | 31.78 ms |
| 選択マスク + アルファロック | 100 | 52.09 ms | 30.56 ms |

これはモザイクの画素演算だけの時間であり、Undo 用の退避・レイヤー合成・
GPU 転送や Windows GUI の応答時間は含まない。

再計測:

```sh
cargo test --release mosaic_performance -- --ignored --nocapture
```

Linux では Cargo の引数に `--features eframe/x11` を追加する。
計測用テストは通常のテスト実行では無視され、時間による合否判定は行わない。

`mosaic_matches_reference_with_masks_locks_and_truncated_buffers` は、
座標単位で元画像を読む参照実装と 720 条件で全バイトおよび返却矩形を比較する。
選択の穴・画像外へはみ出す選択・欠損マスク・アルファロック・不完全な画素バッファ・
画像外の領域・ブロック幅 0/1/2/4/10/100 を組み合わせる。
平均は従来の加算順と f32 演算を保ち、丸め方も変えない。
既存テストでプレビュー・キャンセル・Undo/Redo も確認する。

## キャンバス更新用画像の直接変換 (2026-09-27)

`canvas_view::extract_sub_image` で、合成済み RGBA の各行を直接 `Color32` に
変換する。切り出し用の RGBA 中間バッファを省き、出力用の容量を最初に確保する。
色変換には従来と同じ egui の関数を使う。

不要になる確保容量は更新領域の画素数 × 4 バイトで、2048×2048 なら 16 MiB、
4000×4000 なら 64,000,000 バイト (約 61 MiB)。これは中間バッファの容量であり、
プロセス全体の RSS の実測値ではない。

測定環境は上記と同じ。旧実装をテスト内の `reference_sub_image` として保持し、
同一プロセスで旧・新の呼び出し順を交互に入れ替えて比較した。初回を除いた
7 試行の中央値。64×64 は 1 試行 1000 回、512×512 は 16 回、それ以上は
1 回ずつ変換し、表には 1 回あたりの時間を示す。バッファの確保・解放を含む。
入力は 4000×4000、不透明画像と透明度 0〜255 が混在する画像の 2 通り。
4000×4000 以外は原点 (173, 173) から切り出す。

| 更新領域 | 透明度 | 旧実装 | 直接変換 |
|---|---|---:|---:|
| 64×64 | 不透明 | 2.34 µs | 2.67 µs |
| 512×512 | 不透明 | 190.60 µs | 141.22 µs |
| 2048×2048 | 不透明 | 4.77 ms | 2.64 ms |
| 4000×4000 | 不透明 | 46.25 ms | 24.04 ms |
| 64×64 | 混在 | 6.42 µs | 5.73 µs |
| 512×512 | 混在 | 440.79 µs | 355.76 µs |
| 2048×2048 | 混在 | 8.67 ms | 6.03 ms |
| 4000×4000 | 混在 | 63.34 ms | 39.47 ms |

小さい不透明領域では約 0.3 µs 増える一方、大きな領域では変換時間と
一時メモリを削減できる。サイズによる分岐を増やさず、単一の変換経路を採用した。
この計測は CPU 側の更新画像の生成だけを対象とし、レイヤー再合成・GPU 転送・
Windows GUI のフレーム時間は含まない。

再計測:

```sh
cargo test --release extract_sub_image_performance -- --ignored --nocapture
```

Linux では `--features eframe/x11` を追加する。
`extract_sub_image_matches_reference_for_offsets_edges_and_all_alpha_values` で
透明度 0〜255 を含む画像について 5,168 通りの切り出しを比較する。
画像端・空領域・単一行/列・画像全体を含め、画素と画像寸法・元画像寸法が
旧実装と完全に一致することを検証する。

## プロジェクトの CRC32 (2026-09-27)

`.dpaint` の保存・読み込みで使う CRC32 を、1 バイトずつの計算から
8 バイト単位の slicing-by-8 に変更した。テーブルはコンパイル時に生成する。
依存 crate、unsafe、起動時の初期化は追加しない。表の定義上の追加容量は
7 KiB (全 8 表で 8 KiB)。ファイル形式と CRC の値は従来と同じ。

測定環境は上記と同じ。固定シードの入力を使い、初回を除いた 7 試行の中央値。
1 KiB は 1 試行 1000 回、64 KiB は 16 回、それ以上は 1 回ずつ測定した。
表は 1 回あたりの時間で、入力の生成・確保は含まない。変更前後の別ビルドに
同じ `crc32_performance` テストを使用した。

| 入力 | 変更前 | 変更後 |
|---|---:|---:|
| 1 KiB | 1.610 µs | 0.378 µs |
| 64 KiB | 105.285 µs | 25.733 µs |
| 1 MiB | 1.739 ms | 0.410 ms |
| 64 MiB | 106.197 ms | 26.665 ms |

CRC 計算単体で約 4 倍。プロジェクト全体の保存・読込時間には、符号化・
ディスク I/O・履歴復元も含まれるため、この倍率をそのまま適用できない。

既知値 (空入力、`123456789`) と独立したビット単位の参照実装で検証する。
オフセット 0〜15、長さ 0〜512 と 65,537 バイトを比較し、端数・
アラインメント・空データを含める。既存の v1/v2/v3 の互換性・保存往復・
破損拒否テストも通過した。

```sh
cargo test --release crc32_performance -- --ignored --nocapture
```

Linux では `--features eframe/x11` を追加する。

## GUI 起動・アイドル (2026-09-27)

CRC32 最適化時点のリリースビルドを、専用 Xvfb・Mesa ソフトウェア OpenGL・Noto Sans CJK
フォントで `DARASK_BENCH=1` により 5 回連続起動した。アプリが記録した
2 フレーム目までの時間は 93 / 100 / 96 / 95 / 99 ms、中央値 96 ms。
OS のファイルキャッシュを落とさない測定で、Windows の起動基準の判定には使わない。

通常 GUI の操作終了後、選択を解除し通知が消えてから 10 秒間 CPU 時間を採取した。
増分は 0.00 秒 (0.0%)。詳細と検証範囲は [VALIDATION.md](VALIDATION.md) を参照。

## 不透明な背景への source-over 合成 (2026-09-27)

`raster::blend_over` の背景アルファが 255 の経路を整数補間へ変更した。
出力アルファは常に 255 なので、各色を
`(source * alpha + destination * (255 - alpha) + 127) / 255` で計算できる。
白紙へ描く半透明ブラシ、不透明背景上のレイヤー、浮動片の合成がこの共通処理を使う。
依存 crate、バッファ確保、unsafe は追加していない。

整数演算はインライン化しない小さな関数に分けた。共通の早期リターンまで
含む関数へ直接組み込むと、透明・不透明ソースの既存経路も遅くなることを
実測したため。背景が半透明の場合は従来の浮動小数点計算を維持する。

`blend_over_opaque_destination_matches_general_formula_exhaustively` で、
source 色・destination 色・source アルファの全 256³ = 16,777,216 通りを
旧 f32 式と比較した。各色チャンネルは独立なので R/G/B それぞれの組み合わせを
網羅し、出力アルファと丸めまで全バイトが一致することを検証する。

測定環境は上記と同じで、同一の高性能コア (論理 CPU 8) に固定した。
4000×4000 の 2 レイヤーを用意し、原点から 64×64 / 512×512 / 4000×4000 を
`Document::recomposite` で合成する。固定シードの RGB を使用する。
「α混在」は上レイヤーの画素アルファが 0〜255、「疎」は 16 画素に 1 画素だけ
α混在で残りが透明。「不透明度128」は上の全画素が不透明で、レイヤー不透明度のみ
128/255 に設定する。それ以外のレイヤー不透明度は 255。

初回を除いた 7 試行の中央値。64×64 は 1 試行 1000 回、512×512 は 16 回、
4000×4000 は 1 回。入力生成・バッファ確保は時間に含めない。
変更前の実行ファイルを保存し、旧→新、新→旧の順で続けて測定した。
表は 2 回の中央値の範囲 (1 合成あたり) で、最速の試行値ではない。

| 背景 / 上レイヤー | 更新領域 | 変更前 | 変更後 |
|---|---|---:|---:|
| 不透明 / α混在 | 64×64 | 70.71–71.30 µs | 15.20–16.91 µs |
| 不透明 / α混在 | 512×512 | 4.46–4.51 ms | 0.92–1.00 ms |
| 不透明 / α混在 | 4000×4000 | 279.64–280.12 ms | 58.99–61.19 ms |
| 不透明 / 不透明度128 | 4000×4000 | 280.75–287.76 ms | 62.99–66.30 ms |
| 不透明 / 不透明 | 4000×4000 | 20.57–20.84 ms | 22.82–23.86 ms |
| 不透明 / 疎 | 4000×4000 | 44.53–46.14 ms | 27.99–28.20 ms |
| 半透明 (α128) / α混在 | 4000×4000 | 279.03–283.21 ms | 277.04–277.82 ms |
| 透明 / α混在 | 4000×4000 | 30.47–32.09 ms | 30.81–31.36 ms |

不透明背景への半透明合成は約 4〜5 倍高速化した。一方、全面が不透明な
4000×4000 同士では約 2〜3 ms 増える。透明背景の 64×64 でも
7.26–7.34 µs → 8.05–8.80 µs と小さな増加がある。
すべての条件が速くなる変更ではない。全 18 条件の結果は
`target/validation/2026-09-27-blend/comparison.json` (git 管理外) に保存した。

この測定は CPU のレイヤー合成処理を対象とし、Undo 記録、描画ツールの
ストローク全体、GPU 転送、Windows GUI のフレーム時間は含まない。

```sh
cargo test --release source_over_composite_performance -- --ignored --nocapture
```

Linux では `--features eframe/x11` を追加する。

## 保存タイルのハッシュ再利用 (2026-09-27)

`.dpaint` の保存時、重複排除で計算済みの content hash をタイルと一緒に保持し、
TILS chunk の書き出しに再利用する。これまで重複していた全タイルの再ハッシュを省く。
ハッシュ関数・保存形式・タイル順序は変更せず、重複判定では引き続き画素データも
比較する。読み込み時のハッシュ検証も維持する。

追加するメタデータは x86_64 で固有タイルあたり 8 バイト。4000×4000 の
1 レイヤーで全 256 タイルが固有なら 2 KiB (Vec の余剰容量・アロケータ分を除く)。
保存中だけ保持し、常駐キャッシュ・依存 crate・起動処理は追加しない。

測定環境は上記と同じで、論理 CPU 8 に固定した。変更前後の実行ファイルを
旧→新、新→旧の順で測定し、表には各回の中央値の範囲を示す。
各条件は初回を除く 7 試行、1 試行につき 1 回の `encode_project_payloads`。
固定シードのランダム RGBA 画像 1 レイヤー、同じ画像を重ねた 4 レイヤー、
白紙 1 レイヤーを使用し、編集履歴はいずれも空とした。

| 画像・レイヤー | 寸法 | 変更前 | 変更後 |
|---|---|---:|---:|
| ランダム画像 × 1 | 1024×1024 | 8.47–8.52 ms | 4.50–4.88 ms |
| 同じランダム画像 × 4 | 1024×1024 | 20.99–21.49 ms | 16.08–16.92 ms |
| 白紙 × 1 | 1024×1024 | 3.85–3.85 ms | 3.64–4.00 ms |
| ランダム画像 × 1 | 4000×4000 | 148.72–155.55 ms | 101.83–105.23 ms |
| 同じランダム画像 × 4 | 4000×4000 | 335.25–338.96 ms | 284.82–288.25 ms |
| 白紙 × 1 | 4000×4000 | 58.71–59.74 ms | 58.33–59.25 ms |

4000×4000 のランダム画像 1 レイヤーでは約 3 割短縮した。白紙は固有タイルが
少ないため効果も小さく、1024×1024 では測定値の範囲が重なる。
タイルの切り出し・重複排除・各 chunk の生成とその内部のメモリ確保・解放を含む。
入力生成・最終出力の解放・ディスク I/O・ファイル書き出し時の CRC 計算は含まない。
保存操作全体や Windows GUI の応答時間の測定ではない。

全 6 条件で、変更前後の出力サイズと META/TILS/DOCS/REVS の各 CRC32 が一致した。
比較は計測外で実施した。衝突候補を意図的に挿入する回帰テストで、異なる画素の
タイルを誤って共有しないことも確認する。既存の形式互換・重複排除・保存往復・
履歴復元のテストも通過した。
ログと比較結果は `target/validation/2026-09-27-tile-hash/` (git 管理外)。

```sh
cargo test --release project_encoding_performance -- --ignored --nocapture
```

Linux では `--features eframe/x11` を追加する。
